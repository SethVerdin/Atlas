# Atlas

490 Senior Project - Team 5

Atlas is a mobile fitness app where users log what they ate and how they trained by
chatting with an AI agent in plain language, such as "two scrambled eggs and a slice of
toast" or "bench press, 3 sets of 8 at 185". The agent turns each message into a draft
the user can edit before saving. It can also give basic fitness advice based on the
user's logged habits.

Guiding principle: **the model interprets, the code computes.** The AI decides what
was eaten or lifted and how much. Nutrient values come from USDA records whenever a
match exists. When no match exists, the AI may estimate them as a fallback (see
[How nutrient values are determined](#how-nutrient-values-are-determined)). All
arithmetic is done in code.

## Stack

| Layer | Technology |
| --- | --- |
| Mobile app | Expo (React Native) + TypeScript |
| API | Node.js + Fastify + TypeScript, running locally for the proof of concept |
| Database | PostgreSQL in Docker |
| AI | Google Gemini Flash (function calling) |
| Food data | USDA FoodData Central |

## How nutrient values are determined

Exact values won't always be available. USDA may have no record for a homemade dish
or a less common food, so the agent can estimate as a fallback. Each food in a meal
goes through these steps:

1. **USDA first.** The agent searches USDA FoodData Central. If a result clearly
   matches, its values are used and the item is labeled **USDA**.
2. **Estimate as a fallback.** If nothing matches but the food's typical values are
   well established (common whole foods, standard home recipes, widely known
   products), the agent estimates calories, protein, carbs, and fat per 100 g. It
   also gives a short reason, such as "typical homemade banana bread recipe". The
   item is labeled **Estimated**.
3. **Ask instead of guessing.** If the food is too vague or unfamiliar to estimate
   reasonably accurately, such as "some pasta thing" or an unknown restaurant dish,
   the agent asks one follow-up question about ingredients, brand, or preparation.
   It does the same when the amount is unknown ("a bowl").

Estimates are checked in code before the user sees them:

- protein + carbs + fat can't exceed 100 g per 100 g of food
- calories must be within 20% (or 15 kcal) of what the macros imply (4 kcal/g
  protein, 4 kcal/g carbs, 9 kcal/g fat)

If an estimate fails a check, it goes back to the agent to fix or to ask the user.
The **USDA** / **Estimated** label is set by the API, not the AI: an item counts as
USDA only if that record came back from a USDA search in the same chat turn.

Every meal is shown as an editable draft, and nothing is saved until the user taps
Save, so the user can correct any value first, estimated or not. The rules for the AI
live in [`api/src/agent/systemPrompt.ts`](api/src/agent/systemPrompt.ts) and the
checks in [`api/src/agent/mealDraft.ts`](api/src/agent/mealDraft.ts). See
[`docs/ai-agent.md`](docs/ai-agent.md) for details.

The app has one screen, **Home**: a chat feed where Atlas drafts meals and workouts,
with **Macros** (left), the **mic** (center), and **Exercises** (right) along the bottom.
Everything on it comes from the API and database. There is no sign-in yet: the API acts
as a demo user that `schema.sql` creates.

Each `package.json` needs its `package-lock.json` beside it. The lockfiles pin exact
package versions so everyone, and CI, installs the same thing. They're long, but
GitHub collapses them in PRs. Commit them whenever `package.json` changes.

## Prerequisites

- [Git](https://git-scm.com/)
- [Node.js 24 LTS](https://nodejs.org/) or newer
- [Docker Desktop](https://www.docker.com/products/docker-desktop/). On Windows it
  also needs WSL 2: run `wsl --install` in an Administrator PowerShell, then restart.
- To run the app on a phone: the **Expo Go** app (iOS App Store / Google Play), on the
  same Wi-Fi network as your computer

## Quick start

Open Docker Desktop and wait until it shows "Engine running". Then:

```
git clone https://github.com/SethVerdin/Atlas.git
cd Atlas
npm run setup
npm run dev
```

`npm run setup` is safe to re-run. It:

1. checks that Node.js and Docker are installed and running
2. creates `.env` from `.env.example` (if you don't have one yet)
3. installs dependencies for `api/` and `app/`
4. starts PostgreSQL and, the first time, loads `database/schema.sql`

`npm run dev` starts both servers in one terminal:

- **API** at http://localhost:3000. Open http://localhost:3000/health and you should see
  `{"ok":true,"db":"up"}`.
- **App:** Expo shows a QR code. Scan it with Expo Go (Android) or the Camera app (iOS).
  Or press `w` to open it in a web browser, or `a` for an Android emulator.

To chat with Atlas, add a Gemini key to `.env` first (`GEMINI_API_KEY=...`, free at
https://aistudio.google.com/apikey), then restart `npm run dev`. Without a key the
screen shows "AI is not set up." The app finds the API on its own: on a phone it uses
your computer's address on port 3000. To point it somewhere else, set
`EXPO_PUBLIC_API_URL` in `app/.env`.

**Database created before the home screen was wired up?** Reset it once so it has the
new tables and the demo user: `docker compose down -v`, then `npm run db:up` (this
deletes local data). Otherwise the feed shows an error like "Demo user ... is missing".

Press `Ctrl+C` to stop both.

| Command | What it does |
| --- | --- |
| `npm run setup` | One-time setup (see above) |
| `npm run dev` | Start the API and the app |
| `npm run dev:api` / `npm run dev:app` | Start only one of them |
| `npm run db:up` / `npm run db:down` | Start or stop the database |
| `npm run lint` | Lint the API and the app (same as CI) |
| `npm run typecheck` | Type-check the API and the app (same as CI) |

## Configuration (`.env`)

All settings live in one `.env` file in the repo root, shared by Docker and the API.
`.env.example` lists every variable with a description. Setup copies it to `.env`.
`.env` is git-ignored: **never commit real passwords or API keys**, and only add new
variables to `.env.example` with empty or placeholder values.

| Variable | Used by | Notes |
| --- | --- | --- |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` | Docker, API | Defaults: `localhost`, `5433`, `atlas`, `postgres` |
| `DB_PASSWORD` | Docker, API | Required. Set it before the first `npm run setup`. Changing it later requires a database reset (below) |
| `API_HOST`, `API_PORT` | API | Defaults: `0.0.0.0`, `3000` |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | API | Needed for chat (`POST /v1/chat`). The API starts without it, but chat returns "AI is not set up." Key from https://aistudio.google.com/apikey. Model defaults to `gemini-flash-latest` |
| `USDA_API_KEY` | API | Used by the agent's food search. Optional: without it the API uses USDA's shared `DEMO_KEY`, which is heavily rate limited. Key from https://fdc.nal.usda.gov/api-key-signup |

## Database

PostgreSQL runs in Docker as a container named `atlas_db` on **port 5433** (not the
default 5432). `database/schema.sql` is loaded automatically the first time the
database is created.

- **Check the tables:** `docker exec -it atlas_db psql -U postgres -d atlas -c "\dt"`
  should list `exercises`, `meal_items`, `meals`, `users`, and `workout_logs`.
- **Reset the database** (deletes all local data, then reloads `schema.sql` on the next
  start): `docker compose down -v`, then `npm run db:up`. Do this after changing
  `schema.sql` or `DB_PASSWORD`.
- **Database tools** (DBeaver, pgAdmin): host `localhost`, port `5433`, database `atlas`,
  user `postgres`, and the password from your `.env`.

## Continuous integration

CI is a set of automatic checks GitHub runs on the code, defined in
`.github/workflows/ci.yml`. It catches broken changes before they reach `main`.

**When it runs**

- On **every pull request**, whatever branch it targets, and again on each new push to that PR
- On **every push to `main`**, for example when a PR is merged
- Pushing again while a run is in progress cancels the old run and starts a new one

**What it checks.** Two checks run side by side, each on a fresh Linux machine with
Node 24 (from `.nvmrc`):

| Check | Step | Catches |
| --- | --- | --- |
| `api` | `npm ci` | Packages that won't install; `package.json` and lockfile out of sync |
| | Lint (ESLint) | Common mistakes and bad patterns, e.g. unused variables |
| | Type-check (`tsc --noEmit`) | TypeScript type errors |
| | Build (`tsc`) | Code that doesn't compile to runnable JavaScript |
| | Validate `docker-compose.yml` | A broken Docker file, or one out of sync with `.env.example` |
| `app` | `npm ci` | Same as above, for the app |
| | Lint (`expo lint`) | Mistakes plus React rules |
| | Type-check (`tsc --noEmit`) | TypeScript type errors |
| | `expo-doctor` | Package versions that don't match the Expo SDK; config problems |

If any step fails, that check turns red on the PR. Click **Details** next to it to see
the log. When both checks are green, the PR is ready for review.

**Run the same checks locally before pushing:** `npm run lint` and `npm run typecheck`.

**What CI doesn't do yet**

- **Run tests.** There are none yet. When there are, add an `npm test` step to the
  matching job in `ci.yml`.
- **Start the app or database.** It checks that the code is valid, not that features work.
- **Deploy anything.**
- **Block merges on its own.** Until a repo admin completes the steps below, a red check
  is only a warning.

**Blocking merges (one-time, repo admin only).** CI reports results on every PR, but
GitHub only blocks merging once the checks are marked required:

1. Repo **Settings → Rules → Rulesets → New ruleset → New branch ruleset**
2. Name: `main`. Enforcement status: **Active**
3. Target branches: **Add target → Include default branch**
4. Enable **Require a pull request before merging**
5. Enable **Require status checks to pass**, then **Add checks** and add `api` and `app`.
   They only appear in the list after CI has run on at least one PR.
6. **Create**

## Making changes

1. Update `main` (`git switch main && git pull`), then create a branch:
   `git switch -c my-change`.
2. Make your changes. Run `npm run lint` and `npm run typecheck` before committing.
3. Push the branch and open a pull request into `main`.
4. Wait for the `api` and `app` checks to pass and for a teammate's review, then merge.

**Adding packages**

- API: `npm install <package>` inside `api/`
- App: `npx expo install <package>` inside `app/`. This picks a version compatible with
  the Expo SDK; don't use plain `npm install` there.
- Commit the updated `package-lock.json` together with `package.json`. Never edit a
  lockfile by hand.
- **Lockfile merge conflict:** keep either version, run `npm install` in that folder to
  regenerate it, and commit the result.
- **CI fails at `npm ci` with "not in sync"**: someone changed `package.json` without
  committing the lockfile. Run `npm install` in that folder and commit the lockfile.

**Adding a configuration variable:** add it to `.env.example` with an empty or
placeholder value and a comment, and to the table in [Configuration](#configuration-env).
Never put real secrets in `.env.example`.

## Troubleshooting

- **"Docker is installed but not running"** or **"failed to connect to the docker API"**:
  open Docker Desktop and wait for "Engine running".
- **"Set DB_PASSWORD in .env"**: your `.env` is missing or has no `DB_PASSWORD`. Run
  `npm run setup` or copy `.env.example` to `.env`.
- **Port 5433, 3000, or 8081 already in use**: another program is using it. Stop it, or
  change `DB_PORT` / `API_PORT` in `.env`.
- **PowerShell: "npm.ps1 cannot be loaded because running scripts is disabled"**:
  Windows blocks PowerShell scripts by default. Use `npm.cmd` instead of `npm` (for
  example `npm.cmd run dev`), or use Command Prompt or Git Bash. To fix it permanently
  for your user: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.
- **Phone can't load the app**: make sure your phone and computer are on the same Wi-Fi.
  On restrictive networks (e.g. campus Wi-Fi), stop `npm run dev` and run
  `npm run dev:api` in one terminal and `npx expo start --tunnel` inside `app/` in another.
  With a tunnel, the app can't find the API by itself: also set `EXPO_PUBLIC_API_URL` in
  `app/.env` to an address your phone can reach.
- **Phone loads the app, but the feed says "Can't reach the Atlas API"**: Windows Firewall may
  be blocking port 3000. When Windows asks about Node.js, allow it on **Private
  networks**. Or test in the browser (press `w`).

### Chat (AI) errors

The app shows a short message. The real cause is in the terminal's `[api]` log lines
("Gemini returned an error").

| App shows | Cause | Fix |
| --- | --- | --- |
| "AI is not set up" | No `GEMINI_API_KEY` in `.env`, or the API started before it was added | Add the key, then restart `npm run dev` (the API reads `.env` only at startup) |
| "The AI is busy right now" | Google rate limit (429) or overloaded servers (503), common on the free tier | Wait a minute and try again |
| "The AI took too long" | No answer within 60 s | Try again |
| "The AI service returned an error" | Usually a key or project problem; see the log rows below | |

| `[api]` log says | Fix |
| --- | --- |
| `Gemini API has not been used in project … or it is disabled` (`SERVICE_DISABLED`) | Open the link in the message, click **Enable**, wait a few minutes. Or create a key in AI Studio, which enables it automatically |
| `API_KEY_SERVICE_BLOCKED` | The key is restricted to other APIs. In Google Cloud Console → Credentials, add **Generative Language API** to the key's allowed APIs, or create a new key in AI Studio |
| `402` `prepayment credits are depleted` | The key's project is on prepaid billing with no credits. Use a key from a project without billing (free tier), or add credits |
| `The caller does not have permission` | The key or its project was deleted or changed. Check https://aistudio.google.com/apikey and create a new key if needed |
| `model not found` / `404` | `GEMINI_MODEL` isn't available to your key. Copy an exact Flash model name from AI Studio into `.env` |

After changing `.env`, restart `npm run dev`. Use test messages only: on the free tier,
Google may use prompts to improve its products.
